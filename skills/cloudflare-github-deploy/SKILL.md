# Cloudflare GitHub Deploy

复用已确认的部署设置，完成“指定代码版本 → 正式域名可用”的闭环。技能提供操作方法，不替代当前任务的授权或项目配置。

## 按需读取

- **更新已有站点**：执行下面的短流程，无需重读首次建站说明。
- **首次发布/改域名/修构建配置**：读取 [setup.md](references/setup.md)。新纯静态项目默认采用 Workers Static Assets + Workers Builds；已有 Pages、框架适配器或其他方式保持原架构。
- **仅当仓库是 `hellen9527/devkit-tools`**：读取 [devkit.md](references/devkit.md) 的已知参数；其他项目不能照抄它的域名、仓库或分析 ID。

## 更新发布短流程

1. 读取项目 `AGENTS.md`、部署配置、构建脚本及最新续作记录；检查 `git status --short`、当前分支和远端。确定这次要发布的改动、生产分支、输出目录、正式域名及自动部署是否开启。只读取必要信息，不打印凭据。
2. 按项目现有命令跑适用测试并做**正式环境构建**；检查本次功能、重要深层链接和手机操作。先准备可审查的改动；若当前分支包含未授权或未完成的其他功能，用隔离分支/工作树只集成本次改动。
3. 检查发布配置：只上传构建产物；构建变量与运行时变量分开；前端构建变量是公开内容，不放密钥。沿用锁文件、Wrangler 版本、路由和域名。新功能依赖未取得的外部 ID 时，区分“代码已准备”和“功能已启用”。
4. 在当前授权范围内提交并集成到**实际生产分支**，推送触发既有 Git 自动部署。不要同时再跑一次本地部署制造竞态。只有未配置自动部署或用户明确选择本地发布时，才在已核对的账号/项目下运行仓库的部署命令。
5. 核对此次提交的构建/部署结果，再从正式 HTTPS 域名验证本次改动。记录提交 SHA、部署 ID（若可读）及实际结果。控制台不可读时，可用本次产物指纹/资源哈希/特有内容证明版本；首页 HTTP 200 或推送成功本身都不能证明新版本上线。
6. 验收通过即停止重复部署/轮询。失败时按构建日志或网络结果定位；没有新证据不循环重试。修复后只重复相关验证。

## 线上验收与续作

- 检查首页、变更页面、关键 JS/CSS 与实际工具操作；静态多页站检查未知路径真正返回 404。API 项目另检查本次接口及路由，不用静态文件成功替代接口验收。
- 公共可索引站点检查正式 canonical、robots/noindex、sitemap；私有站或预览保留原索引限制。站点地图提交成功不等于搜索引擎已收录，部署不自动包含 SEO/统计账号开通。
- 问题版本恢复：优先按仓库流程生成可追踪的修复/回退提交；若使用 Cloudflare 历史部署，记录目标版本并同步后续 Git 状态。数据库/外部状态不能靠代码回滚恢复。
- 需要登录、平台新增授权或额度不足时，完成其余独立工作，保存续作记录：仓库/分支/SHA、域名/项目、构建参数、已验证与未验证事项、阻塞原因、下一步。只记录授权范围，不保存密码、令牌、Cookie 或验证码。沿用会话已有授权，不重新问相同权限；新增权限按实际工具要求处理，不把旧项目权限复制给新项目。
- 向用户报告：发布的功能、正式网址、实际验收结果和剩余事项。若只保存了代码，就明确尚未上线。
