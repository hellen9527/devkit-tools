# DevKit 上线前评估

评估日期：2026-09-05。结论：已有可继续开发的产品原型，14 个工具足够作为首版范围；优先修正确性和操作体验，再完善搜索入口和部署。

本次检查包含全部源码审阅、桌面浏览器操作、390px 窄屏检查，以及从原始脚本运行的样例检测。没有修改网站功能，也没有发布网站。样例检测使用模拟 DOM，不能替代真实浏览器的完整回归测试；不能据此宣称所有工具已通过测试。

## 1. 现有工具与优先处理项

| 工具 | 检查发现 | 建议 |
| --- | --- | --- |
| 时间戳 | 源码中 Now 总写入秒值，即使选择毫秒；时钟更新会删除日期子节点 | 修单位联动；显示时区；支持 UTC 日期输入和复制 |
| JSON | 浏览器复现 9223372036854775807 被格式化为 9223372036854776000；字符串中的数字也被错误着色 | 保留原始数值精度，修高亮；加缩进、折叠、下载 |
| URL | 使用原生编码方法；说明把 component 与 whole URL 的保留字符规则写反 | 修说明；补查询参数解析与示例 |
| Base64 | 中文和 emoji 往返通过；/w== 解码变成替换字符，不能保留任意二进制 | 文本模式明确限定 UTF-8；另加文件模式，修 binary-safe 宣称 |
| Hash | 四算法 × 七输入，共 28 组与 Node 标准库一致 | 支持空字符串哈希；增加文件哈希和大输入性能测试 |
| JWT | 原脚本运行复现：过去的 iat 和 nbf 均标 EXPIRED | 分开解释签发、生效、过期；签名未验证时避免笼统 valid |
| Regex | 浏览器用 \\d+ 匹配 abc123，抛出 escOffset is not defined | 修必经报错；后续放入可终止的 Worker，避免复杂表达式卡住页面 |
| UUID | 抽样输出符合 v4 外形；未做完整随机性审计 | 任意数量、下载，后续考虑 v7；安全随机不可用时应明确失败 |
| HTML Entities | 中文编码缺少十六进制 x 前缀，emoji 被拆为代理对；往返结果错误 | 按 Unicode 码点处理；补标准实体映射 |
| Color | rgba(255,0,0,0.5) 转 HSL 丢失透明度 | 保留 alpha；完善短 HEX、百分比透明度和输入校验 |
| curl | 空参数被丢弃；PowerShell 输出的带 & URL 未加引号 | 修参数保真与 shell 转义；复杂语法无法支持时明确报错 |
| Cron | DOM/DOW 按 AND；下一次执行可能是已过去的当前分钟；5junk 被当成 5 | 明确 cron 方言；修日期匹配、未来时刻和严格校验 |
| CIDR | 192..1.1 被接受；/24junk 被当成 /24 | 严格验证 IPv4、前缀；说明 /31 点对点及 /32 语义 |
| HTTP 状态码 | 桌面参考结构清晰；390px 窄屏说明被挤成细竖列且横向溢出 | 手机用状态码/名称一行、解释下一行；逐条核对标准内容 |

关键源码位置（对应评估时版本）：JSON 1045、1073；JWT 1345；Regex 1388；HTML 1463；curl 1587、1668；Cron 1720、1774；CIDR 1811；时间戳 1032、1040；Color 1565。

### 可复现证据

- 浏览器：正则输入 `\d+`，文本 `abc123`，点击 Test；控制台显示 `ReferenceError: escOffset is not defined`。
- 浏览器：JSON 输入 `{"id":9223372036854775807,"text":"abc123"}`，点击 Format；ID 被改变且页面仍报告 Valid JSON。
- 脚本：HTML 全字符编码 `中文😀` 得到 `&#4E2D;&#6587;&#D83D;&#DE00;`，解码无法还原。
- 脚本：`curl -d '' https://example.com` 分词结果丢失空字符串，造成请求参数含义变化。测试只检查生成文本，未执行生成的网络命令。
- 脚本：`0 0 1 * 1` 的下一批结果只包含恰好为星期一的每月 1 日。传统 cron 在两个日期字段均受限时应匹配任一条件，详见 [POSIX crontab](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/crontab.html)。应明确声明方言并按其规范测试。
- 脚本：JWT 中过去的 iat/nbf 均被标记 EXPIRED。三字段含义不同，详见 [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)。
- 浏览器：390px 视口下 HTTP 状态码页面内容容器宽 380px、滚动内容宽 413px；说明列出现逐词换行。

运行样例检测：在项目根目录执行 `node docs/audit-checks.cjs`。结果为观察值，不是自动判定全部通过的测试套件。首次保存结果在 `audit-results.json`；时间相关结果随运行时间变化。

## 2. 界面评价

当前深色、橙色强调、统一线条图标和左侧分类有完整风格，适合程序员；无需推翻视觉方向。操作页直接显示输入和输出，不要求登录，也没有当前启用的广告，这是好的基础。

建议优先做以下调整：

1. 输入和输出成为页面主体。扩大编辑区，支持全屏、长文本和行号，减少卡片内外重复留白。
2. 提高说明和标签对比度；输入文字从 12.5px 调整到更易阅读的尺寸。正文可用普通无衬线字体，代码保留等宽字体。
3. 全站可访问的工具搜索、最近使用/收藏、键盘快捷键；最近使用只保存工具名称，不默认持久化用户输入。
4. 统一示例、清空、复制、下载和交换输入输出。无结果时不要复制占位文字；输入变化后避免让旧结果看起来仍然有效。
5. 手机表格改堆叠布局，检查所有工具的宽度、触控、软键盘；导航补焦点管理、Esc 关闭和展开状态标记。
6. 错误指出原因和修正方法，给表单加可访问名称及结果提示；最后再加浅色主题。

源码未见实际追踪/上传工具输入的逻辑，但页面使用 Google Fonts，会向第三方请求字体。建议自托管字体，隐私文案准确表述“工具输入在本机处理”，避免“任何数据都不会离开浏览器”的绝对承诺。未来加入统计或广告时必须同步更新说明。

## 3. 工具是否齐全

作为首版，14 个已经足够。以下是基于开发工作流的产品判断，并非关键词搜索量调研：

- 优先增强：JSON 的大整数、折叠和文件导入导出；时间戳时区；Regex 的稳定性；curl 的转换保真。这些决定用户能否信任产品。
- 下一批新增：文本/JSON Diff；JSON ↔ YAML；JSON ↔ CSV；SQL Formatter；文本大小写、去重、排序。
- 再往后：进制转换、文件 Hash、UUID v7、cron 时区和方言切换。
- 暂缓：依赖服务器的在线 HTTP 请求、DNS 查询、远程文件处理等。这些会引入网络跨域、运维和滥用处理成本。

建议围绕一个明确用途组织首版：快速处理接口调试中遇到的 JSON、Token、URL、curl 和时间。首页承诺可收敛为“Private developer tools. Fast, free, in your browser.”，不必强调 Every tool 或尚未实现的 one keystroke。

## 4. 建站方案

你已经有网站代码，尚缺的是可靠的发布版本、托管和正式域名。

- 域名：网站的门牌。先确定品牌和可注册域名，按注册商实时价格购买，留意续费价。
- Cloudflare：存放和分发网站文件。无需先购买 VPS、数据库或服务器运维服务。
- GitHub：代码版本记录，便于回退、审查及自动发布。仓库可保持私有。
- Google Search Console：了解 Google 能否发现页面、哪些页面已收录、哪些查询带来点击。

截至评估日，[Cloudflare Pages 官方首页](https://developers.cloudflare.com/pages/)已建议新项目使用 Workers。建议本项目采用 **Cloudflare Workers Static Assets + 独立域名 + GitHub**。Workers 可以只托管静态文件，名字中有 Workers 不代表必须编写后台。其[静态资源请求免费且不限次数](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)；未来添加后台执行则按相应规则和额度计费。

Pages 仍支持静态 HTML，现有 `_redirects` 也是这条路线的配置。若选择 Pages，建议从 Git 集成开始；[Direct Upload 项目不能原地切换为 Git 集成](https://developers.cloudflare.com/pages/get-started/direct-upload/)。两种路线不必同时部署。

建议发布流程：

1. 先修上述正确性问题，补有代表性的回归样例。
2. 将单个约 103KB HTML 拆成共享样式、工具逻辑和页面模板；给每个工具生成独立 HTML。保持纯前端计算，无需为了 SEO 引入运行中的服务器。
3. 发布目录单独使用 `dist/`，只包含网站产物；不要把 `_backup/`、本评估文档和测试脚本上传为公开资源。
4. 创建 GitHub 仓库，配置 Cloudflare 的静态资源发布；先用预览地址测试入口、刷新、复制和错误路径。
5. 绑定正式域名，检查 HTTPS，统一主域与 www，处理预览域名的索引策略。
6. 更新站点真实域名，再提交 Search Console。

暂未登录任何账号、购买域名、创建远程仓库或公开发布。

## 5. 当前 SEO 缺口与处理方式

SEO 让搜索引擎能发现、理解并展示有用的页面。部署成功、提交 sitemap、被收录、获得排名和点击，是不同阶段；不存在加一段代码就保证排名的做法。[Google SEO 入门指南](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)也明确不保证索引或排名。

现有基础包括英文页面、干净路径、动态标题/描述、结构化数据和 sitemap，但仍有以下问题：

| 现状 | 处理 |
| --- | --- |
| robots.txt 和 sitemap.xml 仍使用 YOUR-DOMAIN | 正式域名确认后统一生成，不手工多处替换 |
| 初始 HTML canonical 是 /，工具页运行 JS 后改成自身路径 | 每个页面直接输出一致、完整的 canonical |
| 全部路径返回同一个首页 HTML，靠 JS 切换 | 每个工具预生成专属标题、说明、内容和内部链接 |
| 未知路径也回首页，且通配 rewrite 返回 200 | 真正不存在的路径返回 404 |
| 工具说明通常只有一两句话 | 编辑器下方提供真实示例、适用场景、限制及常见错误 |
| 缺少独立的 About / Privacy / 联系反馈入口 | 加入准确的站点介绍、数据处理说明和反馈方式 |

Google 可以执行 JavaScript，当前单页结构并不等于完全无法收录；但本项目的初始 canonical 与运行时不一致，应优先修复。独立静态页面也有利于不执行 JS 的分享预览抓取。[Google JavaScript SEO 指南](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)支持这些处理方向。

每个工具页建议内容顺序：标题和一句用途 → 工具本体 → 一组输入输出示例 → 限制/常见错误 → 相关工具。不能为了 SEO 把长篇介绍放在输入框前面。

上线后在 Search Console 验证域名所有权，提交 sitemap，用 URL 检查抽查工具页，然后根据展现、点击和收录问题迭代。[Google sitemap 文档](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)说明了提交方法。无需在首版购买 SEO 服务或急着接广告。

## 6. 建议执行顺序与验收

1. **正确性**：先修 JSON、Regex、HTML、JWT、Cron 和 curl，再修其余边界。转换不能静默修改数据；不支持的格式必须明确提示。
2. **使用体验**：加大编辑区、统一操作、改善错误提示，逐页检查手机；选择有价值的大输入做性能测试。
3. **可发布结构**：独立工具页面、正确元信息、真实 404、干净发布目录、构建和回归命令。
4. **上线和收录**：域名、Cloudflare、HTTPS、Search Console；上线后检验实际响应与抓取情况。
5. **迭代**：先看反馈及搜索数据，再决定补哪些工具。暂不以广告收入或工具总数作为首版成功标准。

本次没有做正式线上性能评分、完整无障碍审计、全浏览器验证、关键词竞争分析或收入测算；这些结论不能从本地样例检查推导出来。
